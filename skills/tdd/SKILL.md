# TDD（狭義のTDD / Red-Green-Refactor）

Kent Beck・t_wadaが示す狭義のTDDに従って実装する。「テストを書く開発」ではなく、
**テストが実装を駆動する**開発サイクルを厳格に回す。テストは設計の手段であり、
品質保証の手段ではない。

## 事前準備

1. **テスト実行コマンドを特定する。** 既存のテストフレームワーク、単体テストの実行方法、
   単一ファイル・単一テストだけを実行する方法を調べる。ここが分からないままサイクルに入らない。
2. **テストリスト（TODOリスト）を作る。** 実装すべき振る舞いを、テスト可能な
   *具体例* の一覧に分解する。抽象的な機能名ではなく「入力→期待結果」の形で書く。
   - 例: ✗「バリデーションを実装」 / ✓「空文字を渡すと ValidationError になる」
   - 明らかな正常系から始め、境界値・異常系を後に置く。
   - リストは TodoWrite で管理する。サイクル中に思いついたテストは実装せずリストに追加する。
3. **リストをユーザーに提示し、着手順の合意を取る。** ここで方針のズレを潰す。

## サイクル

テストリストから **1つだけ** 選び、以下を1周する。1周が終わるまで次の項目に触れない。

### Red — 失敗するテストを書く

- プロダクトコードを **1行も書かずに** テストを書く。
- テスト名は仕様を表す文にする。実装の詳細（メソッド名・内部構造）を名前に持ち込まない。
- 期待値から書く（assert first）。期待値は計算式ではなくリテラルで直書きする。
- テストを実行し、**失敗を目で確認する**。ここを飛ばさない。
- 失敗が「意図した理由」で起きているか確認する。想定と違う理由（typo、import漏れ、
  セットアップ不備）で落ちている場合はテストを直してから進む。
- コンパイルエラー・NameError も Red として扱う。ただし1周で解消できる範囲に留める。

### Green — 最速でテストを通す

- 目的は「通すこと」だけ。設計の美しさ・一般性は次のRefactorで手に入れる。
- **通すためにテストを緩めない。** 期待値の書き換え、skip、アサーションの削除は禁止。
  テストが間違っていた場合だけ、その理由を明示してテストを直す。
- テスト以外の失敗（既存テストの破壊）が出たら、先にそれを直す。
- 全テストを実行し、**全部グリーン**を確認する。

### Refactor — グリーンのまま設計を改善する

- 重複を除去する。Green で作った仮実装をここで本実装に育てる。
- テストコードもリファクタリング対象。ただしプロダクトコードとテストを同時に変えない。
- リファクタリング中に **振る舞いを追加しない**。必要になったらテストリストに積む。
- 各リファクタリング後にテストを実行し、グリーンを維持していることを確認する。
- 改善点がなければ「なし」と判断してよい。無理に手を入れない。

サイクル終了後、テストリストの当該項目を完了にし、次の1つを選ぶ。

## Green の実装戦略

Green のとき、以下から意図的に選ぶ。どれを選んだかを報告に含める。

| 戦略 | 内容 | 使うとき |
| --- | --- | --- |
| 仮実装（Fake It） | 期待値をベタ書きして通す | 実装方針に自信がない、テストの正しさを先に確かめたい |
| 三角測量（Triangulation） | 2つ目・3つ目の例を追加し、一般化を強制する | 仮実装から一般解への道筋が見えない |
| 明白な実装（Obvious Implementation） | 正しい実装を直接書く | 実装が自明で、書き間違える不安がない |

原則は「不安なら仮実装から、自信があるなら明白な実装」。明白な実装で2回続けて
失敗したら仮実装に戻して歩幅を狭める。

## 歩幅の調整

- 詰まったら歩幅を小さくする。テストをより小さな具体例に分割する。
- 順調なら歩幅を広げる。ただしテストを2つ同時に書くところまでは広げない。
- 15分以上グリーンにならなければ、最後のグリーンまで戻して（`git stash` / 変更破棄）
  より小さいテストから再開する。粘って積み上げない。

## 禁止事項

- テストなしでプロダクトコードを書く（既存の振る舞いを変えないリファクタは例外）。
- テストを書いた直後に失敗を確認せず実装に進む。
- 一度に複数のテストを書く。
- 実装を通すためにテストを弱める・skipする・削除する。
- Refactor フェーズで機能を追加する。
- 実装を先に書いてから、それに合わせてテストを後付けする（テスト後追いはTDDではない）。
- モックで内部実装を写し取ったテストを書く。モックは外部I/Oと不安定な依存の隔離に限る。

## 報告

1サイクルごとに簡潔に報告する。冗長な実況はしない。

```
[N/M] <テスト名>
Red: <失敗メッセージの要点>
Green: <採用した戦略> / <触ったファイル>
Refactor: <行った改善 or なし>
```

## コミット

- コミットするのは **グリーン かつ Refactor 完了** の時点のみ。
- 1コミット = 1サイクル（1つの振る舞い）を基本とする。
- コミットメッセージはリポジトリの規約に従う（`feat:` / `fix:` 等）。

## 適用しないケース

以下はユーザーに伝えて通常の実装に切り替える。TDDを形だけ被せない。

- 振る舞いを変えない純粋なリファクタリング・リネーム。
- 設定ファイル、依存追加、生成コードの更新。
- 探索的な調査コード（動かして仕様を確かめる段階）。この場合は捨てて、
  分かったことをテストリストにしてから改めてTDDで書き直す。
